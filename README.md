# Guardian

A small health-check monitor hosted on **Vercel**, with a 5-minute external
scheduler and persistent incident state in **Upstash Redis**. It confirms
failures before alerting, sends one **Telegram** notification per incident and
another on recovery, and shows the last scheduled check on its **dashboard**.

```
cron-job.org ──(every 5 min)──▶ https://<app>.vercel.app/api/cron?key=SECRET
                                         │ runs all checks
                                         ├─ Redis → confirm/deduplicate incidents
                                         ├─ incident/recovery → one Telegram message
                                         └─ returns JSON summary

browser / hourly heartbeat ──▶ last completed snapshot in Redis
```

## Why an external scheduler?

Vercel's free (Hobby) plan **caps cron jobs at once per day** and is serverless
(no always-on process, so `setInterval` can't drive a recurring task). So we host
the app on Vercel and let a free scheduler (**cron-job.org**) call `/api/cron`
every 5 minutes. Everything stays on free tiers.

## What counts as "down"

- Any non-2xx HTTP status (500, 502, 503, 404, …)
- No response: request timeout (default 8s), connection refused, DNS/TLS failure
- Optional per-target `expectStatus` — if set, only that exact status is "up"

(Slow-response and response-body checks are intentionally left for later.)

GET/HEAD probes retry failures up to **three times**, one second apart, stopping
on the first success. A failed scheduled run is **pending confirmation**. The
target becomes unreachable after **two consecutive scheduled failures**: at the
5-minute cadence, this adds about five minutes after the first failed run.
Custom methods such as POST are never retried because they may have side effects.

Only a new incident or recovery sends an alert. Transitions discovered together
are combined into one message. Redis keeps incident state across Vercel instance
replacements; a distributed lock prevents overlapping runs, and requests within
four minutes reuse the previous result rather than confirm twice. A gap over
ten minutes resets unconfirmed failure streaks.

Alerts describe reachability **from Guardian's location**. Retries cannot prove
an application crashed or eliminate a persistent network routing problem.
For independent geographical confirmation, add a second monitoring location.

The dashboard and hourly reports read the same saved snapshot. They do not run
competing probes. Data older than ten minutes is marked **stale / unknown**;
the hourly report sends a monitor warning instead of an all-clear.

## Endpoints

| Route | Purpose |
|-------|---------|
| `GET /` | HTML dashboard (calls `/api/status`, auto-refreshes ~30s) |
| `GET /api/status` | Reads the latest saved snapshot, including `pending` and `stale`. Never alerts. |
| `GET /api/cron?key=SECRET` | Runs confirmed checks, saves state, sends incident/recovery transitions. Secret-protected. |
| `GET /api/heartbeat?key=SECRET` | Sends the saved snapshot, or a stale-monitor warning. Secret-protected. |

## Configure your targets

Edit [`targets.json`](targets.json):

```json
[
  { "name": "My API", "url": "https://api.example.com/health" },
  { "name": "Marketing site", "url": "https://example.com", "timeoutMs": 8000, "expectStatus": 200 }
]
```

Per target: `name` and `url` are required; `method` (default `GET`),
`timeoutMs` (default `8000`), and `expectStatus` (default: any 2xx is OK) are
optional. Add `group` (project name) and `label` (e.g. `Server`/`Client`) to
have the summary message grouped per project:

```json
{ "group": "Tulip", "label": "Server", "name": "Tulip Server", "url": "https://api.tulip.ge/api/v1/health" },
{ "group": "Tulip", "label": "Client", "name": "Tulip Client", "url": "https://tulip.ge/" }
```

## Environment variables

Set these in **Vercel → Project → Settings → Environment Variables** (and in a
local `.env` if you run locally — see `.env.example`):

| Variable | What |
|----------|------|
| `TELEGRAM_BOT_TOKEN` | Bot token from [@BotFather](https://t.me/BotFather) |
| `TELEGRAM_CHAT_ID` | The chat that receives alerts (negative id for a group, e.g. `-100…`) |
| `TELEGRAM_TOPIC_ID` | *(optional)* Forum topic id (`message_thread_id`) to post into a specific group topic |
| `CRON_SECRET` | A long random string that protects `/api/cron` |
| `UPSTASH_REDIS_REST_URL` | Manual setup: permanent Upstash Redis HTTPS REST URL |
| `UPSTASH_REDIS_REST_TOKEN` | Manual setup: its read/write REST token; read-only tokens cannot save state |
| `UPSTASH_KV_REST_API_URL` / `UPSTASH_KV_REST_API_TOKEN` | Alternative pair, generated by Vercel Marketplace when the connection prefix is `UPSTASH`. Used when the manual pair is unset. |
| `GUARDIAN_STATE_KEY` | Optional: Redis namespace; defaults to `guardian:{monitor}:v1`. Use distinct keys for Production and Preview/Development. |
| `DISPLAY_TZ` | *(optional)* IANA timezone for alert timestamps, e.g. `Asia/Tbilisi`. Defaults to `UTC`. |
| `ALWAYS_NOTIFY` | *(optional)* `on` intentionally sends a summary every run. Keep unset/`off` for incident/recovery notifications only. |

> Don't have the Telegram values? Create a bot with **@BotFather** to get the
> token, send your bot a message, then open
> `https://api.telegram.org/bot<TOKEN>/getUpdates` and read `result[].message.chat.id`.

## Deploy to Vercel

Before deploying this version, create a **permanent** Upstash Redis database on
the Free plan. In Vercel's **Storage** page, connect it to this project's
**Production** environment with custom prefix **UPSTASH** and **Sensitive**
enabled. Vercel generates the supported `UPSTASH_KV_REST_API_*` credentials.
Keep Preview/Development disconnected from production incident state.
For manual setup, add the `UPSTASH_REDIS_REST_*` pair instead. Do not use an
expiring scratch database or enable paid automatic upgrades. See
[Upstash REST setup](https://upstash.com/docs/redis/features/restapi).
No new npm dependency is required; Guardian uses Redis's HTTPS API directly.

1. Push this repo to GitHub.
2. In Vercel, **Add New → Project**, import the repo, and deploy (no build step
   needed — Vercel serves `public/` and the `api/` functions automatically).
3. Configure the required environment variables above, then **Redeploy**.
4. Run the authorized cron endpoint once to populate the initial snapshot;
   the dashboard reports no snapshot until this first scheduled check completes.
5. Confirm the dashboard loads at `https://<app>.vercel.app/`.

The function duration is explicitly 60 seconds to allow confirmation attempts
and bounded Redis/Telegram requests. If state is missing, invalid or unavailable,
cron returns **503** and sends no outage alerts. Monitor scheduler failures as
well as the hourly report: storage failure pauses alert processing instead of
reverting to the old repeated-message behavior. Avoid flushing the state key;
doing so forgets notification history.

Telegram delivery and Redis acknowledgement cannot share a transaction. Failed
deliveries are retried on the next scheduled run. A function terminated after
Telegram accepts a message but before its acknowledgement is saved can still
duplicate that message. Normal repeated and concurrent runs are deduplicated.

## Set up the 5-minute heartbeat (cron-job.org)

1. Create a free account at <https://cron-job.org>.
2. **Create cronjob** with:
   - **URL:** `https://<app>.vercel.app/api/cron?key=<CRON_SECRET>`
   - **Schedule:** every 5 minutes
3. Save. It will now hit `/api/cron` every 5 minutes; confirmed incidents and
   recoveries generate Telegram messages.

> Prefer not to put the secret in the URL? Configure cron-job.org to send an
> `Authorization: Bearer <CRON_SECRET>` header instead — both endpoints accept either.

### Optional: hourly "all clear" heartbeat

`/api/cron` (every 5 min) only messages you on incident/recovery transitions (with
`ALWAYS_NOTIFY` off). To also get a periodic status report regardless of state,
create a **second** cron-job.org job:

- **URL:** `https://<app>.vercel.app/api/heartbeat?key=<CRON_SECRET>`
- **Schedule:** every 1 hour

You'll get a `🕐 Hourly status` summary of every service each hour, on top of the
incident/recovery alerts. Its timestamp is the last completed scheduled check,
which may be several minutes before the report is sent.

## Run locally

Env vars are loaded automatically from `.env` (via Node's `--env-file`); `.env` is
gitignored. A `CRON_SECRET` is generated for you — just add your Telegram values.

```bash
# 1. Status table in the terminal (no Telegram needed)
npm run check

# 2. Local dashboard + API (requires configured Redis and an initial cron snapshot)
npm run dev:local

# 3. Send real Telegram alerts for any down target (after filling .env)
node --env-file=.env scripts/run-once.js --notify

# Full Vercel emulation (optional, needs `vercel login`)
npx vercel dev
```

## Tests

```bash
npm test
```

Tests cover retries, response cleanup, confirmation/reset rules, duplicate and
overlapping runs, recovery, storage/lock failures, rejected Telegram deliveries,
shared snapshots and stale data. External Redis and Telegram calls are replaced
at the HTTP boundary. `npm test` discovers only `test/*.test.js`; it never runs
the manual `scripts/test-alert.mjs` that can send a real message.

This repository has no configured TypeScript or ESLint checks. Use `npm test`
and `node --check` for its JavaScript files.
